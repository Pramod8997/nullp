## 2. Root causes found and fixed

### F-1 — bulb and fan could not be recognized: no prototype, no envelope

**Failure:** `_classify_device` never returns `bulb`/`fan` — the shipped enrolled
registry (`weights_demo/prototype_registry_enrolled.pt`) had no prototypes for
them, and the physical envelope gate (`_eligible_classes`) has no watts band for
them either.

**Root cause:** the demo fleet (`simulate_esp32.DEMO_DEVICES`) had no bulb/fan
nodes and `scripts/enroll_demo_devices.py` targeted the old 4-class scope. The
recognition path needs *both* a prototype and an enrolled envelope — the envelope
is the independent absolute-watts channel (per §0b M-6 in
`debug_status.md`).

**Fix (existing paths only, no new ML):**
- Added `node_bulb` (60 W / var 4) and `node_fan` (75 W / var 6) to
  `DEMO_DEVICES` in `backend/scripts/simulate_esp32.py`.
- `enroll_demo_devices.py`: `REQUIRED_CLASSES` → the 5 scope names, `NODE_FOR_CLASS`
  maps `phone`→`node_charger`, `bulb`→`node_bulb`, `fan`→`node_fan`.
- Regenerated `backend/models/weights_demo/prototype_registry_enrolled.pt`:
  10 classes, 6 envelopes — phone 44.2–47.9 W, laptop 116.7–122.3, bulb 59.5–60.4,
  projector 297.4–301.9, fan 74.2–75.6, desktop_computer 245.4–253.3.
- Also fixed the class-name mismatch: the shipped registry used the UK-DALE wire
  name `phone_charger` where the scope says `phone` (a check-class-name/index
  mismatch fix, per the ML FIX STRATEGY — no retraining).

### F-2 — no API route from "Unrecognized" to a labeled class

**Failure:** the labeling hook existed in the pipeline
(`handle_label_submitted`) but there was no REST surface taking
`{"signature_id", "label"}` — the operator had to POST raw segments.

**Fix:** in `src/api/main.py` —
- `_capture_signature()` buffers the LABEL_REQUEST event's watts segments,
  embedding, power and confidence per device (bounded at 200, async, lock-guarded),
  wired into the existing LABEL_REQUEST MQTT branch.
- `POST /api/v1/appliances/label-unrecognized` (API-key protected): uses
  buffered segments or request-supplied segments; pydantic validators refuse
  embeddings-as-segments (exactly-128 length, finite, ≥ 0 W, max ≥ 20 W — the same
  contract as `handle_label_submitted`); enrolls via a lazily-built
  `FullPipeline` in `asyncio.to_thread`; broadcasts LABEL_SUBMITTED; audit-logs.
- `GET /api/v1/appliances/signatures/unrecognized` lists the buffer +
  `target_classes` (the prompt for the labeling UI).
- Config: `classes` + `open_set_threshold: 0.65` set in **both**
  `config/config.yaml` and `config/config.demo.yaml`; `appliances:` in the demo
  profile = exactly the 5; `system_safety` max_w entries for the 5 classes.

### F-3 — old 4-class test pins broken by the regenerated registry

The 7 assertions in `tests/test_ml_pipeline_recognition.py` that pinned the old
4-class registry state (class count 7→10, the 65 W "unrecognised laptop"
fixture now lands inside fan's padded envelope 62.9–86.9 W, `monitor` no longer
enrolled) were re-anchored: the unrecognized-laptop test moved to **95 W** — the
true gap between the fan ceiling (86.9 W) and the laptop floor (~99 W). The
class-count and envelope assertions were updated to the 10-class/6-envelope
state, and `TestFourRequiredClassesAreRecognised` → `TestFiveRequiredClassesAreRecognised`.
